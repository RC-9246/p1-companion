# 二十项原计划的逐项复核（2026-10-24）

> 此页保留早期设计/验收记录；v0.21 的实现、五轮验证方法与仍未证明的目标见[最新逐项核对](design-verification-20261029.md)。

结论：20个方向均有工程对应，但不能把这句话等同于原表所有细节均已完整完成。此前“全部完成”的表述过满；以下区分已有能力、简化实现与尚缺的验收。测试次数、模块就绪和服务健康不能代替逐项效果与真实动作的证据。

## 本次真实运行检查

P1可连接；135项生产清单无源码漂移；8个容器运行，核心健康检查通过；4个运行数据库quick_check均为ok；两个浏览器无僵尸进程。检查时可用内存约1960MB。这些只证明本次运行基础状态。

动作账本在一次最近一小时统计窗口中有14次failed、1次complete，旧记录只保存ValueError，没有具体代码。因此当前后台自主可靠性仍是未通过项。两次仅规划诊断和一次P1本机临时副本的完整隔离回合成功，不能据此认定真实失败已修复；没有向真实QQ发送诊断消息。

新增故障码确认两次真实失败均为research阶段的research_no_result。进一步核对发现共享公开读取额度60/60已用完，Bing公开RSS实际仍可访问；旧规划不感知该额度，把耗尽后的研究继续选中，并把预算拒绝误当作检索故障。这是本次实际定位的预算衔接问题。

本次补充受控的失败码和阶段记录：只记录实现中列举的错误枚举，不保存原始异常中的聊天正文、模型文本、账号或凭据。先部署的诊断补丁通过299项回归、原生自主集成和故障账本去敏测试。后续修复把公开检索/读页额度设为所有范围共享240次/UTC日，保留原计数，不改变模型API额度；规划器收到剩余额度与可选活动，耗尽后可整理或休息，竞态耗尽与模型预算耗尽按quiet处理，不再机械记作failed。新的预算状态读取不扣额度、按原日期规则重置，权限和发布边界保持不变。修复的最终实测结果见evidence/twenty-item-budget-postflight.json；不能把预算衔接修复说成所有自主质量问题已经解决。

## 验收结论的使用方式

历史299×5轮、41项隔离故障与真实模型合成评测仍有价值，但不证明全部真实动作已端到端验收、全模块AI代码自修复、长期人格像人或十年无故障。原表不应继续被标记为“所有细节全部完成”。优先补齐后台自主失败定位与修复，再分别补原子提醒改期、任务自主改优先级/放弃、记忆事件关联、受检媒体转发、B站持久进度与资料库、以及受控代码修复管线。

最终验证：301项回归、5轮预算专项共25项、原生自主/范围矩阵以及中性核心134项和5项原生预算检查通过。真实公开搜索和Python官方页读取成功；随后真实后台动作账本出现research=complete，发生在修复部署之后。历史失败保留，不把它们删除后宣称零故障。该恢复只解决已确认的额度衔接问题，不改变上表其余缺口。
