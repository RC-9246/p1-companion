# 自修复与恢复

宿主机每三分钟检查一次，独立看门狗每十分钟检查修复机制。检查逻辑不依赖模型正常工作；模型只能读取去敏状态、请求下一次检查、在隔离工具中做有限实验，不能把网页/聊天给出的命令直接变成生产命令。

## 自动处理的故障

- 八个插件的缺失/变化文件：只从root保护的已验证检查点恢复，拒绝被改坏的检查点和不在清单中的路径。
- 固定MCP/浏览器辅助代码、Compose、备份/巡检程序及服务单元：已验证副本恢复；必要时重载服务。
- 三个内部工具令牌：只恢复已封存的当前内部令牌，不生成新权限，不导出内容。合法轮换后必须重新封存。
- 八个容器停止、消失或异常：连续三次失败才处理；先重启，持续故障时用已记录镜像ID重建，保留既有卷与网络；不拉取未知最新版。
- 六类SQLite：先验证备份，停止拥有者，再隔离坏文件和WAL/SHM，恢复通过校验的快照。没有有效备份就保留原件，不猜修复内容。
- 恢复后不重放未知发送；旧提醒作废，旧自主任务暂停；记忆退回候选或清除不确定的派生内容，防止旧备份复活后续已取消/遗忘事项。
- 低内存、低磁盘、高温或明显时钟跳变：暂停可选后台活动，尽量保留聊天，不自动删除用户文件。
- 解析子进程超时、失控循环、浏览器进程清理：限定CPU/内存/输出/进程数，父服务保持可用。

每服务30分钟冷却、每天最多两次修复。健康数据库六小时保存一次验证快照，保留十四代。既有每日数据库、配置和工作流备份继续存在。对长期运行，管理员还应检查原有备份保留量，并将重要恢复点离机保存；机器内的备份不能抵御整盘损坏。

## 隔离验收

`tests/isolated_repair_acceptance.py` 只对临时文件、合成数据库和 `p1-repair-lab-worker` 操作。临时容器无网络、无生产数据挂载。包含八插件文件缺失、源码变化、坏检查点拒绝、六类数据库恢复、坏备份不覆盖、权限配置关停、资源降级、真实容器崩溃/缺失/重建、镜像ID保持、修复引擎恢复、失控实验、重试冷却与部署互斥锁。测试前后比较八个生产容器的启动时间和重启次数，要求完全相同。

生产补丁还实际触发过一次回滚：旧巡检与部署并发。已改为共享文件锁；不把systemd oneshot的activating状态当成已停止。故障原始证据留在P1，不用删除失败证据来制造全绿结果。

## 手动控制与回滚

QQ主人命令 `/自修复 关闭` 暂停自动修复；`/自修复 开启` 恢复。宿主机也可在 `plugin_data/affect/maintenance.disabled` 建立或删除标记。模型没有改这个开关的工具。

回滚前停止两个修复timer，等待已在执行的检查结束，并取得 `maintenance.lock` 排他锁。避免恢复程序把人工回滚误判为文件损坏。

中性安装的安装前恢复点由bootstrap生成，保存在目标root/backups/install-时间戳。运行 `sudo python3 scripts/restore.py 恢复点绝对路径 --apply` 恢复原插件/原配置，保留数据库和被替换文件，并保持自动修复关闭，待人工核对与重新封存。数据库快照留在恢复点，仅在确认影响范围、冻结旧发送账本并检查遗忘语义后恢复；不静默覆盖健康数据库。生产分支的历史固定部署器不作为新机器的安装入口。

自修复只对已经列举并验证的动作自动执行。宿主机无法启动、Docker守护进程/内核损坏、硬件或磁盘故障、平台封号/验证码、账号主动撤销、付费失败、第三方API实质变化和未知程序逻辑错误仍需要外部恢复或人工处理。十年稳定目标需要持续维护，不能由一次短期验收保证。

检查点包含固定文件的UID、GID和权限位。恢复校验同时检查字节和访问权限；令牌需要服务可读，备份需要可执行，依赖代码的浏览器/代理需要重载。`tests/portable_leisure_install.py`在无网络、无账号、无生产挂载的临时安装上恢复代码与令牌后，启动真实非root服务验收。
