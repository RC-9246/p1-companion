# 图片来源混淆排查与修复（2026-10-24）

本次排查确认了一次错误图片描述：当前私聊消息只有简短文字、没有图片附件，模型却给出具体画面，随后又在对方否认时坚持是对方发送的，并猜测账号或转发异常。这些断言没有依据。

## 实际核查结果

- 对比同一范围的 QQ 收件记录、AstrBot 对话内容、附件结构与长期记忆读取键；问题消息的当前图片附件数为 0。
- 同一对话仍含 34 个历史图片部分，旧图片与当前消息缺少足够明确的来源约束。
- 按生产注入代码实际使用的用户、会话和关系三个键检查，当前共有 1 条生效的长期记忆，里面没有这次具体画面描述。候选记忆没有当成生效记忆注入。
- 没有查到这次画面描述从另一个会话的文字或正式长期记忆进入的证据。具体画面是否由某张旧图片诱发，无法从现有记录确定；不能据此断言全部记忆系统永远不会串入。
- 确认的缺陷是：生成前没有明确区分当前附件与历史图片，生成后没有针对缺图、用户否认发图的独立检查。原有短回复复核缺少附件证据，不能承担这一检查。

没有依据支持账号被盗、另一个设备代发或 QQ 平台重推消息等判断。

## 修复方式

1. 在正常私聊和已启用群聊的请求最后阶段，加入由事件与请求结构生成的附件证据：直接图片数、当前模型可见图片数、是否含引用或转发、历史图片部分数。不会把图片 URL、文件路径、账号或图片内容加入这个证据摘要。
2. 明确区分历史图片、引用资料、助手表情包与后台视频采样。历史助手说过什么，不能证明用户真的上传过什么。
3. 增加独立于模型额度的输出检查。没有当前图片、也没有同一发言者近期真实图片回执支持的模糊指代，不允许输出具体图片判断；对方否认发图时，不再用自身旧回答证明或猜测账号异常。
4. 保留真实当前图片和有回执、仍有历史图片输入的近期跟进问题。只在同一会话、同一发言者、十分钟窗口内认可近期图片来源；群内别人的图片不能替代当前发言者的图片。
5. 对本次核实错误的 6 条助手回复采用范围隔离的精确摘要撤回：只在模型请求副本中替换这些错误回复，原始对话记录保持不变。没有清空对话，没有删除或合并其他人的记忆。

精确撤回清单位于私有数据目录的 `media_retractions.json`。键是内部会话范围，值是已核实错误的助手纯文本去除首尾空白后的 SHA-256 摘要数组。模型不能通过普通目标、资料或偏好工具修改该清单。只替换匹配的助手消息，用户和工具消息保持原样。生产清单、真实对话及账号信息不随公开源码发布。

## 验证与恢复

- 308 项离线回归测试通过，其中包含缺图、否认发图、无依据账号猜测、真实图片、历史跟进、助手自身图片、精确撤回不修改原文等用例。
- 实际 AstrBot SDK 验证请求与响应钩子、两个独立范围、撤回不跨范围；另验证记忆读取范围和现有/新加私聊与群聊的模块矩阵。
- 在已安装生产代码中，用原始对话在设备本地重放请求组装及回复检查；当前附件数为 0，6 条错误助手回复被隔离，原始对话摘要一致。此过程没有发送 QQ 消息，也未把真实历史额外发给模型。
- 现有 DeepSeek 服务上的三个合成用例通过：缺图指代、否认发图、普通文字上下文；没有额外发送真实私聊历史或 QQ 消息。
- 四个生产数据库检查正常；八个容器运行；135 个生产文件与发布清单一致。

部署前保留私有数据库一致性备份，通过现有发布器备份旧代码、启动回滚看门狗、重启并检查健康、更新恢复点。恢复代码使用对应部署恢复点运行 `tools/deploy_patch.py --rollback <恢复点>`；精确撤回清单有独立私有备份。不要以清空全部记忆作为图片幻觉的默认修复方法。

这些检查针对已定位的故障及相邻情形，不能保证消除模型全部事实错误。对于具体历史图片内容，仍应以实际附件与回执为准。
