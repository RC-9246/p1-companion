# Linux、Tailscale 与容器解析故障排查

一次真实恢复中，宿主机 `/etc/resolv.conf` 是Tailscale写入的普通文件，而systemd-resolved的本地stub被关闭。`resolvectl query` 能使用DHCP上游，但普通应用和旧容器的公共域名解析失败。修复宿主机后，已经运行的容器仍保留旧上游；只检查宿主机不足以证明机器人恢复。

本次按 [Tailscale Linux DNS说明](https://tailscale.com/docs/reference/linux-dns) 恢复systemd-resolved stub模式，保留Tailscale DNS与网络策略，使用设备已有DHCP解析器，没有硬编码生产网络地址或添加公网端口。具体步骤须按本机解析器、53端口占用、VPN和网络管理服务确认，不能照抄到所有Linux系统。

1. 保存原解析文件/链接、resolved配置与网络状态，准备限时自动回退。分别检查宿主机的普通解析、resolved查询、AstrBot容器的公共解析与内部服务名。
2. 确认53端口无冲突、systemd-resolved和网络管理方式；按官方说明启用stub并将resolv.conf连接到stub文件，重启相关解析服务。先验证主机与Tailscale都正常，再提交修复。
3. 必要时在维护窗口刷新受影响容器的解析配置。优先少量目标服务，核对原有镜像、挂载、网络与端口；不重建登录资料、不开放内部网络的外连。内部浏览器/解析容器本就可能禁止直接公共DNS，应通过受限出口和真实页面读取验证。
4. 单独检查QQ登录状态与OneBot连接。本次QQ进程一直运行，却停在已有账号的登录按钮；用已保存账号重新登录后，API的online/good与TCP连接均恢复。勾选自动登录不保证将来无需验证码，安全挑战仍需人类处理。
5. 最后验证公开页面、内部健康、私人账号会话状态、数据库、生产源码清单和恢复检查点。遇到browser_busy要尊重单浏览器限额，等待后重试；不能把健康HTTP=200当成完整功能验收。

部署中发现核心链路未就绪，发布器实际执行了回滚；恢复QQ和解析后再部署。回滚成功只证明恢复机制对这次故障起效，不能证明十年零故障。生产备份、账号、tailnet后缀、私有地址和截图不随本页公开。
